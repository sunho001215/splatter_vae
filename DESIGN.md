This supplements [the continuation design](docs/ours_ext_20261113.md). All edits are confined to this worktree. The external design note, main checkout, queues, run directories and the original 200k checkpoint are unchanged.

## Entry-point acceptance

Both new scripts use the established `_bootstrap` preamble and an unindented `guard_gpus()` call before importing training code. `tests/test_ours_priority.py` compiles the scheduler's actual `GUARD_CALL` and `check_guarded` definitions from its AST and runs that acceptance function against both script files. It never imports a campaign entry point or executes either GPU script. Like existing launched scripts, these scripts now guard even before `--help`.

## Priority and starvation

Every candidate order uses numeric queue `priority` first (default 5, smaller first), followed by its previous key. Registration age, campaign rank, companion status, seed, encoder-pilot rank and family fairness cannot put an older priority-2 FQL row ahead of priority -1 Ours pretraining or priority 0 Ours FQL. Equal-priority behavior retains the previous ordering and capacity policy.

Paths audited and covered:

- Scheduler eligibility already orders `(priority, registration order)` and accepts negative priorities in `load_queue`; both local and remote ticks now also protect blocked priority tiers for GPU slots/memory, host RAM, CPU threads and disk.
- Remote `dispatch_key` prefixes its old key with priority. Remote candidates and movable pool units are planned in shared ascending priority tiers, keeping remote-first ordering within ties. Pool units keep their old internal order and rollback behavior.
- Remote release batches group by `(priority, release, image)` and dispatch in priority order. A higher-priority ready, feasible batch row still pending after its scheduler tick reserves its exact capacity for subsequent batches. Different release pins cannot bypass the ordering. The release-chain driver itself has no campaign-row rank: `drive()` delegates its verification rows to the same scheduler. `pick_native_gpu()` ranks devices, not jobs; its existing device-choice key is unchanged. Existing release verification reservations and acceptance gates remain prerequisites for campaign work.
- Baseline local candidate sorting prefixes the complete previous order with priority, and passes priority into fair-share selection. Fair-share runs the unchanged family policy one priority tier at a time, charging earlier admissions as active reservations. Family guarantees and short-evaluator exceptions apply within a tier. A waiting ready, feasible row reserves one MIG and its host resources; lower tiers may use the remainder.
- The baseline driver's Stage 2 yield now preserves higher-priority candidates. The Stage 2 driver prefixes its old rank with priority, reserves capacity for higher-priority local ready rows served by another driver, and checks GPU/RAM/CPU/disk capacity before admission.
- The local placement planner already sorted by priority. It now protects exact waiting-row reservations and considers existing pending local reservations in priority order, excluding lower-priority unstarted rows while placing a higher tier. Running reservations are always charged. The pool mutation helper only changes host fields; its sorted list of moved IDs is not a dispatch order. Compatibility scripts in `runs/setup/tools` delegate to these implementations and were not edited.

**Backfill choice (user directive 2026-11-13 ~16:20):** maximise useful GPU/MIG utilisation on both hosts, with Ours pretraining before Ours FQL before other approved work. A waiting row reserves capacity only when it is ready (dependencies done, not paused, role/ownership allowed, release and mirror inputs satisfied) and feasible on an empty approved host device and within the host's total RAM, CPU and disk budgets. Infeasible or not-ready rows reserve nothing and receive a per-pass diagnostic.

Process waiting rows in queue-priority order. Each reserves one specific eligible MIG, choosing the most free GPU memory, then the fewest live jobs, then device order. Running occupancy is always included. Each row also reserves its full declared host RAM, CPU threads and disk; measured admission footprints may increase the RAM charge. Multiple waiting rows reserve distinct MIGs and sum their host needs, bounded by the available MIG count. The reservations are rebuilt from live state on every pass; no reservation file or registry state is introduced.

Strictly lower tiers can use other MIGs only when admission leaves the complete sum of higher-tier RAM/CPU/disk reservations available. Their jobs never enter reserved MIGs, even when a small refill would fit alongside the running work. Equal-priority ordering, hybrid-head rules, family fairness and evaluator exceptions retain their established behavior. Running jobs are never stopped, moved, signalled or preempted. As jobs drain, their capacity accumulates for waiting higher tiers while unrelated capacity remains useful for approved experiments.

This replaces the former whole-host hold, including its indefinite hold for impossible requests. It preserves priority without requiring remaining-runtime estimates: lower-tier jobs use only resources outside the explicit reservations. Scheduler local/remote ticks, remote/pool planning and failed pool claims, fresh release-batch dispatch, baseline fair-share, Stage 2 and local placement use the same pure reservation helper. A release batch re-reads live resource evidence and cumulatively charges its filtered rows; a refused or failed claim keeps only a ready, feasible row's exact reservation. Local drivers dispatch their selected MIGs so the scheduler cannot repack a lower-tier row into a protected instance.

All priority consumers in `ops/jobs` and `ops/campaign` were searched. No new nonnegative check was introduced. Tests load -1 through real queue validation and exercise competing ready priorities -1, 0, 2 and default 5. The coordinator's reprioritization of other rows is assumed as directed. The 0..9 operator `set_priority` tool/range is unchanged; the registrar writes explicit negative queue priorities directly.

## Complete AdamW resume

`validate_resume_state` now receives an optimizer built from the actual CPU model. Before staging or accepting the source/latest checkpoint it requires every parameter ID in every saved group to have exactly one state entry, the saved/live group counts and lengths to agree, both moment tensors to match the corresponding live parameter shape, and every scalar step counter to equal the checkpoint step exactly. Missing, extra or duplicate states, missing groups, fractional counters and incompatible shapes fail closed. The existing scheduler/science/schedule checks remain.

Continuation training also requests the same strict check inside `load_checkpoint`, before any state is loaded, so direct continuation-loop resumes cannot bypass it. Legacy loads retain their previous default behavior. The wrapper's temporary validation model/optimizer remain on CPU and are released before training starts.

Tests remove a state from a later group, remove a whole group, corrupt either moment shape and both shapes together, and change counters; both wrapper validation and strict checkpoint loading reject them. The actual tiny CPU train loop compares uninterrupted continuation with two resumed jobs at `num_workers=0` and `num_workers=2`, crossing an epoch boundary. LR, model weights, optimizer state, RNG restoration and sampled indices remain identical. This validates the deterministic multiworker stream without running the full real-data/GPU model.
